## 0. 三个必须先做的决定

| # | 决定 | 为什么必须先决定 |
|---|---|---|
| **D1** | 主指标用什么 | 实测：基线 **10 次提案就到 95.2% 改进**（见 §1.2）。"相对初始点的改进率"已饱和，用它做主指标会得出"所有方法都差不多"的空结论 |
| **D2** | 预算轴用什么 | 实测：基线 **2.1 s/求值**，智能体 **200–350 s/求值**，差 **~100×**（见 §1.1）。用「求值次数」我们赢，用「墙钟」我们输 100 倍。必须两个都报，并说清哪个是真实瓶颈 |
| **D3** | 无效设计点怎么算 | 实测：基线在第 2 次求值就 **崩溃退出**（见 §1.3）。智能体有重试/修复、基线没有 → 不统一处理，对比直接失真 |

## 1. 四个前置问题（都有实测证据）

### 1.1 成本严重不对称 → 决定 D2

| 方法 | 每次求值耗时 | 证据 |
|---|---|---|
| 传统基线 | **≈ 2.1 s** | `rs / vit_tiny / budget=10` → 11 次求值 23.59 s，扣除 ~13 s 固定启动（torch + CACTI + MCP 握手） |
| 智能体 | **≈ 200–350 s** | `runs/run_agent/legacy/sweep_buggy_latency/sweep_summary.jsonl`：1-iteration 运行 390–690 s（2 次求值 + 5 个阶段 LLM） |

**这不是仿真慢，是 LLM 慢。** 单次 SimPhony 仿真只要 2 s，而一次智能体提案要 5 个阶段、
每个阶段多轮 ReAct 工具调用。

**设计后果**：

- 不能只说"同预算下我们更好"。审稿人一定会问"你们的预算里算不算 LLM 成本？"
- 正确做法：**主角是求值次数，但必须配一个等墙钟对照**（§2.2 的 C-a）。
- 唯一站得住的辩护：**在真实光子 DSE 里，一次求值的代价远高于 2 s 的 CPU 时间**——
  若接 TCAD / FDTD / 流片回环，单次求值是分钟到小时级。所以"少求值"是真实需求。
  这句话必须写进正文，否则 D2 无从辩护。

### 1.2 改进率饱和 → 决定 D1

实测 `rs`（随机搜索）在 vit_tiny 上，初始 objective **10204.4**：

| 总求值次数 | best-so-far | 相对初始改进 |
|---:|---:|---:|
| 1（初始） | 10204.4 | — |
| 3 | 8297.5 | 18.7% |
| 5 | 6519.9 | 36.1% |
| 7 | 1535.4 | 85.0% |
| **9** | **489.5** | **95.2%** |

> 注：`baselines.runner` 打印的 `eval N` 是第 N 次**提案**（不含基线），
> 上表已换算成**总求值次数**（含初始点）。首提案 11716 比初始点更差，
> 所以第 2 次求值的 best-so-far 仍是 10204.4。

而 `ITERATION_SUMMARY.md` 里智能体在**同一初始点**上的最好成绩是 **4952.8（51.5%）**。

**结论：随机搜索在 9 次求值内就超过了智能体的历史最好成绩。**
这不是坏消息——它揭示了一个更有价值的问题：

| 总求值次数 | 智能体（历史） | RS（best-so-far） | mock 纯框架 |
|---:|---:|---:|---:|
| 2 | **4952.8（51.5%）** | 10204.4（0%） | 8699.4（14.75%） |
| 5 | 4952.8（51.5%） | 6519.9（36.1%） | ⟨待测⟩ |
| 7 | 4952.8（51.5%） | **1535.4（85.0%）** | ⟨待测⟩ |
| 9 | 4952.8（51.5%） | **489.5（95.2%）** | ⟨待测⟩ |

**智能体在极低预算下反超，随预算增长被反超 → 存在交叉点（本例在总求值 5–7 之间）。**

这是本文最有说服力的叙事：**"智能体的价值在「求值极其昂贵、只允许一两次提案」的
区间"**，而不是"我们全面更强"。设计必须把交叉点测出来。

**设计后果**：
- 主指标改成 **log 空间的 gap-closed**（§2.1），不再用「改进率」
- 预算轴改为 **扫描点** `{1,2,4,8,16}`，而不是固定 50 —— 更省机时，且正好覆盖交叉区
- 负结果要有预案：若交叉点很低（比如 2 次），主张收敛为"零样本预算下的先验注入"

### 1.3 无效设计点导致崩溃 → 决定 D3

实测 `rs / vit_tiny / seed=1` 在第 2 次求值时整条 run 崩溃：

```
json.decoder.JSONDecodeError: Expecting value: line 1 column 1 (char 0)
  baselines/harness.py:173 -> evaluator.evaluate -> adapter.evaluate
  -> _evaluate_via_mcp -> json.loads(_unwrap_text(out))
```

根因链：
1. 某些硬件点（如 `core.width=1`、缺器件槽位的组合）让 SimPhony 抛异常；
2. `bridge/mcp/simphony_server.py:109` 的 `evaluate` **没有 try/except**，异常被 MCP
   包装成错误文本返回；
3. `bridge/mcp/simphony_tool.py:115` 直接 `json.loads()` → 崩；
4. `baselines/harness.py` **没有任何异常捕获** → 整条 run 终止。

**不公平之处**：智能体侧有 LangGraph 的 `RetryPolicy` + `_repair_duplicate`，遇到无效点
能退回来重提；基线侧直接死。于是"基线"这个条件包含了「因崩溃而丢数据」，
而"智能体"这个条件不含。

**设计后果（这个改动是 5.2 能否成立的前提）**：
- 在 `baselines/evaluator.py` 与 `simphony_tool.py` 加统一处理：
  捕获异常 → 记为**不可行点**（`objective = +inf`, `invalid = True`），**不中断 run**
- 智能体侧同样把不可行点记为 `+inf`，**不允许**用重试把它藏起来
- 所有表都报 **invalid rate** 列
- 否则审稿人只要复现到一次崩溃，就能质疑整张表

### 1.4 智能体没有种子 → 影响统计设计

`cli.py` 无 `--seed`，`build_chat_model` 也不传 `seed`。而基线侧有 `--seeds`
（`random.Random(seed)` 注入，逐位可复现）。

**设计后果**：
- 智能体的多次运行**无法配对**，只能当作独立样本 → 用非配对检验
  （Mann-Whitney U），统计功效更差
- 也无法复现某一次具体运行 → 审稿人无法核对
- 建议补一个 `--seed`（同时控制 `ChatOpenAI(seed=...)` 与温度），把两类方法
  都变成「种子配对」，用 Wilcoxon signed-rank，功效立刻上来

## 2. 三节共用的方法论

### 2.1 主指标：log 空间的 gap-closed（替代"改进率"）

对每个 workload 定义 best-known：

$$ \text{obj}^\* = \min\{\text{所有方法、所有预算、所有种子下见过的 objective}\} $$

主指标：

$$ \text{GC} = \frac{\log \text{obj}_{init} - \log \text{obj}_{run}}{\log \text{obj}_{init} - \log \text{obj}^\*} \in [0,1] $$

**为什么这样定义**：
- objective 是 `latency × energy × area`，跨 **9 个数量级**（实测 10204 → 489），
  算术平均会被极大值支配 → 必须在 log 空间
- 以 `obj*` 为上界，**自动扣掉「初始点太差带来的送分」**，这就是解决 §1.2 饱和的钥匙
- 取值 `[0,1]` 且与 workload 无关 → 可跨 workload 加总，也便于画一张总结图

辅助指标：
- **Evals-to-target**：达到 `GC = 0.90 / 0.95 / 0.99` 所需求值数（达不到记为 ∞）
- **最终 objective**（log 尺度，原始值也报，便于领域读者核对）
- **invalid rate**、**success rate**

### 2.2 预算轴

- **主轴：SimPhony 求值次数**（`{1,2,4,8,16}`），理由见 §1.1 的辩护
- **副轴：墙钟时间**，单独一列，不做主排序
- **成本：tokens/run**（`common/metrics.py` 已聚合，写在 `metrics.json`）

三轴同时报，让读者自己判断在哪个尺度上权衡——这比只报一个轴更可信。

### 2.3 统计

| 项 | 做法 |
|---|---|
| 重复数 | 每 (workload, method, budget) **n = 10** 个种子；算力不够时降到 5 并在 limitation 声明 |
| 中心趋势 | **中位数 + IQM**（四分位均值），不报算术均值 |
| 离散度 | 95% **分层 bootstrap** 置信区间（按 workload 分层重采样） |
| 配对比较 | 有 `--seed` 后：**Wilcoxon signed-rank** |
| 非配对比较 | 无 `--seed` 时：**Mann-Whitney U** |
| 多重比较 | **Holm–Bonferroni** 校正（5 个基线 × 4 个 workload = 20 组，不校正会被抓） |
| 效应量 | **Cliff's δ** 或中位数比，必须给（p 值小不等于差异大） |

### 2.4 运行有效性（必须先定义，否则数字没法挑）

一条 run 记为**有效** iff：
1. 退出码 0
2. 至少 1 次有效求值
3. 未触发预算超限

崩溃 / 超时 / 全 invalid 的 run：**保留在分母里**报 invalid rate，**不静默剔除**。
（静默剔除失败 run 是最常见的作弊指控来源。）

### 2.5 预注册

把矩阵、预算、指标、阈值写进仓库（一个 `EXPERIMENT_PROTOCOL.md`）再开跑。
这件事本身就能挡掉"事后挑指标"的质疑，且你已经有了 `--at-budget` 这类工具支持。

## 3. §5.2 与传统方法对比的设计

### 3.1 研究问题

> **RQ1**：在**同等仿真求值预算**下，LLM 多智能体能否比模型无关搜索找到更好的光子
> 加速器配置？该优势在什么预算区间成立？
>
> **RQ2**：该优势是来自"更聪明的决策"，还是来自"更大的可达动作空间"或"内置规则回退"？

RQ2 是防守性但必须回答的问题，否则 RQ1 的结论会被归因为平凡原因。

### 3.2 处理与对照

| 条件 | 配置 | 作用 |
|---|---|---|
| **Agent** | 五阶段流水线，DeepSeek-V4-Pro | 处理组 |
| **RS / SA / BO / GA / Sweep** | 统一动作空间，同种子 | 主对照 |
| **C-a 等墙钟 RS** | RS 预算 ×100（≈1000 evals），匹配智能体墙钟 | **回答"是不是只是花的时间多"** |
| **C-b 复合动作 RS** | RS 每次提案改 k=4 个参数（对齐智能体一次多编辑） | **回答"是不是只是动作空间大"** |
| **C-c 无回退 Agent** | 禁用 `_repair_duplicate` | **回答"是不是靠内置规则"** |

**C-a / C-b / C-c 是三个"一击致命"的对照，不做的话 RQ1 无论如何都站不住。**
好消息是前两个只是给 `baselines.runner` 加参数，第三个只需一个开关。

### 3.3 动作空间对齐（公平性契约的核心）

传统算法只能做「参数移一格 / 切一次模板 / 换一个器件变体」的最小合法编辑，
与智能体工具箱能力对齐。**必须在正文用一句话写死**：

> All methods operate on the same unified action space and share the same
> evaluator, search space, initial hardware, and budget accounting; therefore
> differences in the results can only stem from the decision policy.

否则"智能体能一次改 5 个参数"会成为对结论的唯一解释。

|---|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|

| vit_tiny | RS | | | | | | | | | | |

横轴 = 求值次数（log2 刻度），纵轴 = 中位 objective（log 刻度），每方法一条，
阴影 = bootstrap CI。**交叉点用竖线标出来**——那是本文的核心发现。

### 3.6 预期结论的三种写法（都要提前想好）

| 若观察到 | 主张 |
|---|---|
| 交叉点在 2–8 次，之后基线反超 | **"智能体适合求值极昂贵的低预算区"**（最可信、最有新意） |
| 智能体全程占优 | "决策策略带来 X% 的额外收益"，但要靠 C-a/C-b/C-c 排掉平凡解释 |
| 智能体全程落后 | 诚实报告，主张转向"多范式/跨层约束带来的**可达性**收益"（那是 §5.3 的内容） |

> 已有实测（2 次求值）：**纯框架 14.75% < 真实 LLM 51.5%**；RS 在 2 次求值为 0%，
> 但在总求值 7 次时升到 85.0%、9 次时 95.2%。
> 这说明差异主要来自模型决策，而框架规则本身不足以取胜——第二/第三种写法须以此为前提。

**第三种情况必须提前准备**——按 §1.2 的实测，它并不遥远。把叙事铺在
"多范式 + 跨层一致性"上，那个结论有 C1/C2/C6 的确定性证据支撑，不依赖 LLM 强弱。

## 4. §5.3 消融实验的设计

分三层，成本从零到低。

### 4.1 第一层：贡献消融（离线、确定性、零机时）✅ 已有

`scripts/experiments/ablation_evidence.py` 的 A–F 直接产出，**这是全仓库唯一能立刻
进论文的数字**：

| # | 被消融组件 | 完整系统 | 消融后 | 观察量 |
|---|---|---|---|---|
| C1 | 跨层共享约束 | violations=0，门控 `pass` | `work_freq=25` → **3 处违规**，`fail→re-execute` | 违规检出数（DAC 14 / ADC 10 / PD 20 GHz 三处同时捕获） |
| C2 | 跨范式搜索 | Pareto 前沿 **2 点** | 仅 crossbar → **1 点** | mesh 面积 **−92.4%**、IL **+9.16 dB** |
| C3 | 联合/顺序调度 | joint：1 轮落地 3 层 | sequential：逐层，其余 deferred | 落地层数、deferred 数 |
| C4 | 门控行 5.5 | 非可求值模板 → `re-execute` | 移除 → **`accept`（放行）** | 决策翻转 |
| C5 | 出处纪律 | 41 变体 **100%** 覆盖 | 无标注裸奔 | 14 可追溯 + 23 标注 + 4 placeholder |
| C6 | 解析式 mesh 求值器 | 可评估模板 **3** | 收缩为 **1** | Reck/Clements 可评估，Butterfly 诚实 non-evaluable |

**写法建议**：这层定位为**机制证据（mechanism evidence）**，不是性能证据。
它证明"每个组件确实做了它宣称的事"，成本为零、可完全复现，是很强的加分项。

### 4.2 第二层：运行期开关消融（CLI 已支持，直接可跑）

| 消融项 | 开关 | 对照 | 观察量 |
|---|---|---|---|
| 证据门 | `--no-gate` | 默认 8 行协议 | GC、被放行的非法提案数 |
| 搜索调度 | `--search-strategy sequential` | `joint` | GC、每轮落地层数 |
| 跨范式预扫 | `--topology-sweep` 关 | 开 | Pareto 前沿大小、GC |
| 状态继承 | `--state-strategy next` | `best`（keep-best） | GC 方差、回归次数 |
| RAG 历史 | 空 store | 有历史 | GC、首轮提案质量 |
| 模型能力 | `--provider mock` | 真实模型 | **分离"框架"与"模型"贡献**（见 §5） |

**这一层性价比最高**：6 组对照，零代码改动，且都是审稿人想看的"去掉会怎样"。

### 4.3 第三层：角色消融（⚠️ 需先加开关）

去掉 model / architecture / topology / device 中某一个智能体，是最标准的组件消融。
**当前 `cli.py` 没有这个开关**。

设计：
- 加 `--disable-stage {model,architecture,topology,device}`（可重复）
- 被禁用的阶段直接输出空结论、不调 LLM（省机时）
- 5 组对照（含全开基线）

**必须同时报"该层是否还被触及"**：去掉 architecture agent 后，如果 solution 仍然
改了架构参数，那这个消融就没隔离住——要检查 `applied_actions` 的层归属。

### 4.4 交互效应（不要只做单因素）

单因素 leave-one-out 只能看出主效应。至少补 3 组交互：

| 交互 | 假设 |
|---|---|
| 约束 × 门控 | 去掉约束后，门控还能不能兜住？（C1 × C4） |
| 跨范式 × mesh 求值器 | 没有 mesh 求值器时跨范式是否退化为单范式？（C2 × C6） |
| 调度 × keep-best | sequential 是否更依赖 keep-best 才能不退步？（C3 × 状态策略） |

### 4.5 消融表格式

| Ablation | GC @16 ↑ | ΔGC vs full | Evals-to-GC0.9 | Invalid% | 结论 |
|---|---:|---:|---:|---:|---|
| Full system | | — | | | |
| − 跨层约束 | | | | | |
| − 跨范式 | | | | | |

| − RAG | | | | | |

否则 ΔGC 不可比。

## 5. §5.4 不同大模型的设计

### 5.1 研究问题

> **RQ3**：框架的收益是否依赖特定 LLM？当模型能力下降时，**确定性护栏**
> （约束检查 / 门控 / keep-best）能否把结果限制在"不进步"而非"变差"？

RQ3 的后半句比前半句有价值得多，也是本文能差异化于"我们又跑了一个模型"的地方。

### 5.2 四个条件（含一个关键的"零智能底线"）

| 条件 | 模型 | 作用 |
|---|---|---|
| M1 | DeepSeek-V4-Pro-0813（paratera） | 强模型 |
| M2 | DeepSeek-V4-Flash（paratera） | 同供应商弱模型 |
| M3 | deepseek-chat（**DeepSeek 官方端点**） | **跨供应商**，最有说服力 |
| **M4** | **`mock`（`FakeToolCallingModel`）** | **零智能底线：只有框架、没有模型智能** |

**M4 已实测**（`--provider mock --iterations 3`，vit_tiny，本次实跑）：

| 求值 | objective | 相对初始 | 说明 |
|---:|---:|---:|---|
| 1（初始） | 10204.4 | — | |
| 2 | 8699.4 | **14.75%** | 纯框架（无模型智能）的首个提案 |
| 3 | 11128.5 | −9.1% | **比初始点还差** → 被 keep-best 拒绝 |
| 4 | 8508.6 | 16.6% | |

于是同一个初始点上，**2 次求值**时的三家排序是：

| 方法 | @2 次求值（1 次提案） | 相对初始 |
|---|---:|---:|
| 真实 LLM 智能体（历史最好） | **4952.8** | **51.5%** |
| `mock` 纯框架 | 8699.4 | 14.75% |
| 随机搜索 RS | 10204.4 | 0%（首提案 11716 更差，被 best-so-far 吸收） |

**这组数字直接回答了 RQ2**：纯框架（14.75%）并不显著优于随机搜索（第 1 次提案 0%），
真正的增益来自模型的语义决策（51.5%，约为 RS 的 2.8 倍）。
这是个诚实、且比"我们全面更强"更有说服力的结论——**框架的价值是"使能"而非"优化"**：
它把 LLM 的推理能力转换成合法、可评估、不退化的搜索动作。

同时，第 3 次求值的 −9.1% 回归被 keep-best 拦下，**在 M4 条件里就现场演示了护栏有效**
（对应 §5.3 的 RQ3 后半句）。

**成本**：M4 无 LLM 往返，约 **37 s/求值**（4 次求值 2.5 min），比真实模型便宜约 7 倍
→ §5.4 里 M4 这一列为几乎零成本。

**M4 是整个 5.4 的支点。** 它把"框架贡献"与"模型贡献"分开：
- 若 M4 也能显著改进 → 收益来自**框架的确定性规则**（约束求解、修复回退、keep-best），
  这恰恰是本文真正的贡献，且与模型无关
- 若 M4 几乎不改进、而 M1–M3 显著改进 → 收益来自模型能力，框架只是放大器
- 两种结论都有价值，且都能写。**这是你独有、且不花 API 费用的条件。**

### 5.3 指标与失败分类

**定量**：GC @16、纯 LLM 驱动率、tool-call 错误率、tokens/run、墙钟、护栏触发次数。

**失败分类法**（定性，但极有说服力）——已从 `docs/results/results.md` 归纳出四类：

| 失败类型 | 实例 | 框架如何兜住 |
|---|---|---|
| 工具参数名错 | 提 `in_bit` 而非 `precision_in_bit` | 校验失败 → 回退 |
| 幻觉器件替换 | 未查面积就换 `ACADEMIA_EO_MZM_1x1`（比 LT_MZM 大 141×） | 仿真真值让 obj 变差 → keep-best 拒绝 |
| 事实错误陈述 | 称 SL_MZM"降低衰减"，未查其 4.5 dB IL | 同上，净收益仍为正 |
| 回归提案 | vit_base 上 height/width 12→16 → area +322.7% | keep-best 拒绝，交付基线 |

一条建议的正文句：

> LLMs make mistakes, but the framework's deterministic guardrails confine those
> mistakes to *failure to improve* rather than *degradation*: across all models,
> every rejected proposal left the best-known design intact.

### 5.4 统计功效：不要 4 workload × 3 seeds

3 个种子无法支撑任何统计结论。建议 **2 个 workload（B1 小 + B3 大）× 5 seeds**：
- 细胞数 4 模型 × 2 workload × 5 seeds = 40 运行，与 4×3=36 差不多
- 但每个细胞的 n 从 3 提到 5，CI 才有意义
- 且"小/大模型"两点足以支撑"规模越大收益是否越大"的趋势陈述

### 5.5 怎么表述"与模型无关"（措辞很关键）

不要写"结果不受模型影响"——数据不会支持。建议：

> Improvements are **directionally consistent** across all backbones (every model
> improves over the initial design and none degrades it), while the **magnitude
> varies with model capability**; the deterministic guardrails hold across all
> models, including the zero-intelligence `mock` baseline.

## 6. 实验矩阵与预算（按实测校准）

成本模型（实测）：智能体 **≈250 s/求值**，基线 **≈2.1 s/求值**。

| 实验 | 组合 | 预算 | 智能体机时 | 基线机时 |
|---|---|---:|---:|---:|
| §5.2 主 | 4 workload × 10 seeds | 16 | 40 × 1.2 h ≈ **48 h** | 200 × 6 min ≈ **3 h** |
| §5.2 C-a 等墙钟 | RS ×5 workload | 1000 | — | 5 × 35 min ≈ **3 h** |
| §5.3 开关消融 | 6 组 × 4 seeds | 16 | 24 × 1.2 h ≈ **29 h** | — |
| §5.3 角色消融 | 4 组 × 4 seeds | 16 | 16 × 1.2 h ≈ **19 h** | — |
| §5.4 多模型 | 3 模型 × 2 wl × 5 seeds | 16 | 30 × 1.2 h ≈ **36 h** | — |
| §5.3 C1–C6 | — | 0 | **0**（离线） | — |

**合计 ≈ 135 h 单机**（约 6 天不间断）。可用两条路降：

1. **并发**：仿真单进程只吃 1–2 核，4 vCPU 可开 **2–3 并发** → 降到 **~50 h**
2. **换快模型**：`--provider paratera-flash` 跑消融与多模型实验，单次求值可从
   250 s 降到 ⟨待测⟩，§5.3/§5.4 的时间大头就没了（**§5.2 主实验仍必须用 Pro**）

**建议的"最小可辩护"矩阵**（若时间紧张）：

| 实验 | 最小配置 | 机时 |
|---|---|---:|
| §5.2 | 3 workload（B1/B2/B3）× 8 seeds × 预算 {1,2,4,8} | ~20 h |
| §5.3 | 6 组开关 × 3 seeds × 预算 8 | ~7 h |
| §5.4 | 4 条件 × 2 workload × 4 seeds × 预算 8 | ~10 h |
| §5.3 C1–C6 | 离线 | 0 |
| **合计** | | **~37 h** |

注意预算用 `{1,2,4,8}` 而非 16——因为**交叉点在低预算区**（§1.2），
高预算段反正会被基线反超，没必要烧机时。
